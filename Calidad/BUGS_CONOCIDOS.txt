## 1. [2026-01-02] Bottom Nav - Múltiples items activos simultáneamente
================================================================================

PROBLEMA:
  El navbar inferior mostraba múltiples items como activos (ej: "Repuestos" 
  y "Voz" al mismo tiempo) cuando el usuario estaba en ciertas páginas.

CAUSA:
  La lógica en mobile-nav.js usaba:
  1. href.split('?')[0] para extraer el path, lo que hacía que "/parts/?voice=1"
     se convirtiera en "/parts/"
  2. startsWith() para matching parcial, que es demasiado amplio
  
  Resultado: Tanto "Repuestos" (/parts/) como "Voz" (/parts/?voice=1) 
  coincidían cuando el path era /parts/add/ o cualquier /parts/*

SOLUCIÓN:
  Reescribir updateBottomNavActive() con:
  - Mapeo explícito por data-nav-id
  - Orden de precedencia de más específico a menos específico
  - Verificación de query params para distinguir "voz" de "repuestos"
  - Solo un item puede estar activo (el primer match gana)

ARCHIVOS AFECTADOS:
  - parts/static/parts/js/mobile-nav.js

COMMIT: 2273eb9

## 2. [2026-01-02] Voice UI - Mala UX en ingesta por voz (REDISEÑO COMPLETO)
================================================================================

PROBLEMA:
  La interfaz de ingesta por voz tenía múltiples problemas de UX:
  1. No se centraba verticalmente en la pantalla
  2. Mostraba todos los comandos disponibles a la vez (muy ruidoso)
  3. Al cambiar de estado, la altura del contenedor cambiaba causando "saltos"
  4. Diseño no optimizado para móvil
  5. Difícil entender en qué paso del flujo estaba el usuario

CAUSA:
  El diseño original fue incremental, añadiendo elementos sin una visión
  de UX coherente tipo "wizard". El CSS no tenía altura fija y los elementos
  se mostraban/ocultaban sin transiciones.

SOLUCIÓN:
  Rediseño completo con patrón "Wizard" (un paso a la vez):
  
  1. Nueva UI con 4 pasos claros:
     - Paso 0: Selección de Taller y Vehículo
     - Paso 1: Escucha de voz (botón grande centrado)
     - Paso 2: Revisión de datos capturados
     - Paso 3: Confirmación de éxito
  
  2. Contenedor con ALTURA FIJA para evitar saltos
  
  3. Solo UN comando visible a la vez (el relevante para el paso actual)
  
  4. Transiciones suaves entre pasos (CSS transitions)
  
  5. Indicadores de progreso tipo dots (● ○ ○ ○)
  
  6. Bridge JS que conecta la nueva UI con la lógica existente mediante
     CustomEvents: handsfree:statechange, handsfree:dataCaptured, etc.

ARCHIVOS CREADOS:
  - parts/static/parts/css/voice-wizard.css (nuevo diseño)
  - parts/static/parts/js/voice-wizard-bridge.js (comunicación con hands-free)
  - parts/templates/parts/part_form_v2.html (nuevo template)

ARCHIVOS MODIFICADOS:
  - parts/static/parts/hands-free-voice.js (emisión de eventos)
  - parts/views.py (usar nuevo template)

PRINCIPIOS DE DISEÑO (ISO 9241-171):
  - Botones grandes para móvil (mínimo 44px touch target)
  - Un solo comando visible por vez
  - Altura fija (--vw-step-height: 420px) evita reflows
  - Centrado vertical y horizontal perfecto
  - Transiciones de 300ms para cambios de estado
  - ARIA labels para accesibilidad

## 3. [2025-12-30] Micrófono Android - getUserMedia falla en Capacitor
================================================================================

PROBLEMA:
  Al usar funciones de voz en la app Android (Capacitor), getUserMedia fallaba
  con "NotAllowedError: Permission denied" aunque el usuario había aceptado
  el permiso.

CAUSA:
  Dos problemas combinados:
  
  1. Faltaba el permiso MODIFY_AUDIO_SETTINGS en AndroidManifest.xml
     WebView requiere AMBOS permisos para audio:
     - RECORD_AUDIO
     - MODIFY_AUDIO_SETTINGS
  
  2. Se había implementado un WebChromeClient personalizado que SOBRESCRIBÍA
     el BridgeWebChromeClient de Capacitor. El de Capacitor ya maneja
     correctamente onPermissionRequest(), pero el personalizado no tenía
     toda la funcionalidad.

SOLUCIÓN:
  1. Agregar a AndroidManifest.xml:
     <uses-permission android:name="android.permission.MODIFY_AUDIO_SETTINGS"/>
  
  2. ELIMINAR el WebChromeClient personalizado de MainActivity.java
     Dejar que Capacitor use su BridgeWebChromeClient por defecto
  
  3. Agregar llamadas a window.requestMicrophonePermission() antes de
     getUserMedia() en los archivos JS que usan audio

ARCHIVOS AFECTADOS:
  - android/app/src/main/AndroidManifest.xml
  - android/app/src/main/java/.../MainActivity.java
  - parts/static/parts/hands-free-voice.js
  - parts/static/parts/recorder.js
  - parts/static/parts/voice-webrtc-hybrid.js
  - parts/static/parts/js/part-list.js

## 4. [2025-12-30] Java syntax - import alias no soportado
================================================================================

PROBLEMA:
  Error de compilación en MainActivity.java:
  "error: ';' expected" en la línea del import

CAUSA:
  Se usó sintaxis de Kotlin para alias de import:
  import androidx.core.graphics.Insets as CoreInsets;
  
  Java NO soporta alias en imports (eso es sintaxis de Kotlin).

SOLUCIÓN:
  Cambiar a import directo sin alias:
  import androidx.core.graphics.Insets;
  
  Y usar "Insets" directamente en el código.

ARCHIVOS AFECTADOS:
  - android/app/src/main/java/.../MainActivity.java

COMMIT: 575e0b7

## 5. [2025-12-30] CSP + Turbo - Scripts inline bloqueados
================================================================================

PROBLEMA:
  Scripts inline con nonce eran bloqueados después de navegación Turbo:
  "Refused to execute inline script because it violates CSP..."

CAUSA:
  Turbo hace navegación SPA: carga HTML vía fetch e inyecta en el DOM.
  Cada respuesta HTTP tiene un NONCE diferente.
  Cuando Turbo inyecta HTML nuevo, el navegador usa el CSP de la página
  ORIGINAL, no el del nuevo contenido.
  
  Resultado: El nonce del script inline no coincide con el CSP activo.

SOLUCIÓN:
  NUNCA usar scripts inline en templates. Siempre archivos externos:
  
  ❌ INCORRECTO:
  <script nonce="{{ csp_nonce }}">código</script>
  
  ✅ CORRECTO:
  <script src="{% static 'parts/js/mi-script.js' %}" 
          nonce="{{ csp_nonce }}" defer></script>

ARCHIVOS AFECTADOS:
  - Todos los templates que tenían scripts inline
  - parts/static/parts/js/app-loading-init.js (reemplaza inline)
  - parts/static/parts/js/style-watcher.js (reemplaza inline)

## 6. [2025-12-09] Turbo Forms - action="" resuelve URL incorrecta
================================================================================

PROBLEMA:
  Formularios dentro de turbo-frames con action="" enviaban POST a la URL
  incorrecta (la de la página principal en lugar de la del frame).

CAUSA:
  Cuando Turbo carga contenido en un frame vía fetch, los forms con action=""
  resuelven la URL relativa a la PÁGINA PRINCIPAL, no a la URL del contenido
  cargado en el frame.
  
  Ejemplo:
  - Usuario está en /autos/ (página principal)
  - Click en "Eliminar" carga /autos/delete/12/ en el frame
  - Form tiene action=""
  - POST va a /autos/ en lugar de /autos/delete/12/

SOLUCIÓN:
  SIEMPRE pasar action_url explícita desde la vista al template:
  
  Vista:
  return render(request, 'template.html', {
      'object': obj,
      'action_url': reverse('parts:mi_accion', args=[pk]),
  })
  
  Template:
  <form method="post" action="{{ action_url }}">

ARCHIVOS AFECTADOS:
  - Todas las vistas de delete, create, update que se cargan en frames
  - parts/templates/parts/confirm_delete.html
